Concepts

How the agents work

Each architecture layer can run an agent that answers its WAF questions from your workspace's own signals — and drafts an evidence-backed verdict for you to review.

Introduction

There is one agent per architecture layer — Ingestion, Storage, Processing, Orchestration, Analytics, AI, and ML. Given an assessment, a layer's agent gathers evidence from system tables, Unity Catalog metadata, and job/pipeline/cluster configuration, then judges each of its questions and writes an evidence-backed finding.

The agent drafts; you decide. Every finding is a suggestion with its evidence attached. You review it, adjust, and set the final status — the score always reflects your decisions, never the agent's alone.

How a run works

The run

Each agent is a small workflow that loads the layer's questions, works out what in your workspace to look at, runs a check for every question it can, and writes the results back.

Triggerapp → run-now → Load questionsfrom waf-data.json → Discover scopecatalogs & objects → Run checkscollect → judge → Write findingsto Lakebase
1️⃣

Trigger

From the assessment page you launch a layer's agent. The Flask app calls the Jobs run-now API for that layer's Job, handing it the assessment id, the catalogs in scope, and where to write results.

2️⃣

Load questions

The agent reads the layer's questions from the canonical set (waf-data.json) at runtime. Because questions live in data, adding one never breaks a run — it simply awaits a check.

3️⃣

Discover scope

The agent resolves which catalogs (and, per layer, which objects) checks run against, so findings reflect your estate. With no catalogs selected it uses every catalog the principal can see.

4️⃣

Run checks & write back

For each question the agent runs its check, streaming progress, then writes findings and a run status straight to Lakebase. A question with no check becomes needs review; a check that errors is caught and skipped.

Progress is streamed while the run is in flight, so the assessment page shows how many of the layer's questions have been evaluated in real time.

Anatomy of a check

The unit of work

A check answers one (or a few) WAF questions. Every check is split into two halves — collect gathers evidence, judge turns it into a verdict — which keeps the evidence explainable and both halves independently testable. More than 240 checks ship across the seven layers.

🔢 Deterministic checks

Where a question maps to a clean number, the check computes a ratio from system tables and compares it to a threshold. For example, "Store data in Delta Lake" counts the share of managed/external tables whose format is DELTA: ≥ 90% is Met, ≥ 60% is Partial, below that is Not met.

Because the answer is a hard fact from a reliable signal, these report High confidence.

🧠 LLM-judged checks

Many practices have no single number — "code is in Git with CI/CD", say. The check gathers the relevant configuration artifacts (job/pipeline definitions, cluster settings, external locations…) and asks a Databricks serving-endpoint model to judge them. Most checks work this way.

The judge rules on only the evidence provided — it can't invent facts, must answer unknown when evidence is thin, and its confidence is capped at Medium.

Graceful by design. A question with no registered check becomes an unassessed finding — Unknown / needs review — rather than an error, so a newly added question never breaks a run. A check that raises is caught, recorded as Unknown, and the run continues.

Every check reads the same signals through one context object. For the full list of what those signals are, see System tables & signals.

Verdicts & statuses

The output

Each finding carries a verdict, a confidence, a rationale, and the evidence behind it. The verdict maps onto the same statuses you'd pick by hand, coloured the same way.

met→Completed
partial→In Progress
not_met→Open
unknown→Needs your review

What confidence means

Confidence Meaning
High A deterministic fact from a reliable signal (e.g. a system-table ratio). Only deterministic checks reach High.
Medium A strong proxy that required reasoning — the ceiling for an LLM-judged verdict.
Low A weak or indirect proxy; a reviewer should verify before relying on it.
None Not automatically assessable — no check, or no signal to judge.

Unknown means the agent had no signal or no check for that question — distinct from you choosing to answer it later. You always review the evidence, adjust, and set the final status; re-run the agent whenever your workspace changes.

Where it runs

Execution model

Agents run only in the deployed Databricks App, using its service principal — no workspace data leaves your account.

⚙️

One Job per layer

Each layer's agent is a serverless Databricks Job, named waf-agent-<layer>. The app finds the right Job by that name and triggers it via run-now.

🔑

Runs as the app SP

Jobs run as the app's service principal, which owns the app's Lakebase schema and is the principal the system-table grants target.

🗄️

Writes straight to Lakebase

The Job writes progress and findings directly to Lakebase (Postgres); the app reads them back for display.

🧩

Model via serving endpoint

LLM-judged checks call a Databricks model-serving endpoint (through AI Gateway). With none wired, those checks return unassessed.

🗺️

The backlog agent

A results-level agent turns a finished assessment into a prioritized backlog. It needs no workspace access, so it runs in the app itself, not as a Job.

👥

Human in the loop

Every agent answer is a draft with its evidence attached. You inspect it, adjust, and own the final status.
